IndexedDB

The app remembers its last server answers on this device, so a returning reader sees their content while fresh answers arrive.

A ghost component in 1 Root: it draws nothing, takes no space and has no focus or pointer target. The app starts its account runtime once from the root; pages read through that runtime. This owner-only App guide documents an existing application pattern, not an exported element or a storage service supplied by DS1.

Open, remember, refresh

  1. Identify the account. Scope snapshots by backend deployment and account ID. Visitors do not start the account download or edit transport.
  2. Read what is already here. Memory, the tab’s session copy and a small allowlist of settings metadata can answer synchronously. IndexedDB hydrates asynchronously, once per scope. A late disk answer cannot replace a newer value or revive an invalidated record.
  3. Draw, then listen. A page receives its cached answer immediately if one exists, with pending local changes projected over it. Its live query stays subscribed. The next server answer replaces the snapshot; a refused query removes its cached answer and reports the error. There is no global loading gate.
  4. Refresh in the background. Startup reads the account’s lists and overview. Lists whose updated_at still matches reuse their held items; the next sync after six hours reads every list again. Up to four list reads run together. Reconnecting starts another sync.
  5. Remember only the changes. Changed query keys are queued for persistence. Switching accounts or signing out clears the snapshot state and queues deletion of the stored account.

What lives where

MemoryThe current scope’s query answers, timestamps, dirty keys and invalidations.
IndexedDBentries: one { value, time } record per query key. meta: the account scope. A scope change clears the previous account’s entries in the same write transaction.

localStorageAllowlisted settings display metadata and sync timestamps. Pending edits are separate records here, not in the IndexedDB snapshot store.

A query key combines its function name and JSON arguments, with object keys sorted recursively. Use non-secret identifiers as arguments; never put credentials or access tokens in snapshot keys or values. The account scope separates caches; the server still decides access.

One record per query

The storage adapter opens a versioned database with two object stores. A read loads its scope, keys and values in one transaction. A write puts changed records and deletes removed keys in one read-write transaction, with relaxed durability. It resolves when the transaction completes and closes the database in finally.

Do not serialize the whole account after every edit. A list already holds its items, so identical item and note snapshots are omitted from disk and derived from the list when it is read back. This deduplication belongs to the application’s data model.

  • Small writes are grouped after 250 ms. Large overview records and the tab copy wait until edits settle for five seconds.
  • Equal answers keep their existing value object and usually write nothing. A server-confirmed unchanged record is eligible for a disk timestamp refresh after one day.
  • Snapshots older than seven days are not used. Expired records encountered during disk hydration are queued for removal.
  • pagehide and a hidden document trigger a full flush. These are best-effort opportunities, not a guarantee that a closing browser will finish writing.

Pending edits stay separate

The snapshot is the last confirmed answer. An edit queue persists local intent and projects it over that answer for immediate feedback. After the server accepts an edit, the queue marks it confirmed, folds it into the snapshots and waits for their quick flush before removing the queued record. If device storage fails, the confirmed record stays queued. A cached read alone is not an offline editing or conflict-resolution system.

Account and failure boundaries

Every asynchronous read, refresh and write checks that its captured scope still matches the active account. Sign-out clears memory, timers, session and settings copies, and serializes the IndexedDB clear after outstanding writes. Storage events detect account changes in other tabs. A profile preference change is not an account switch.

Opening the database times out after two seconds and rejects blocked or failed opens. Startup refresh stops after 30 seconds. Failed snapshot reads are optional: the app continues with memory and live queries. Failed writes restore dirty keys for a later flush. Storage can be unavailable or cleared by the browser, so snapshots are a cache, never the only copy of the reader’s work.

Wiring in the app

These are the reference implementation’s module responsibilities, not imports from the App package:

initializeApp.ts
Starts the account runtime on initialization, account changes, navigation and reconnect; skips visitors.
startupStorage.ts
Owns database opening, transactions, per-query records and clearing the stored scope.
querySnapshots.ts
Owns memory, hydration, freshness, deduplication, batching and persistence failure handling.
startupSync.ts
Collects account data, reuses unchanged lists and schedules full refreshes.
cachedQueries.ts
Delivers cached answers, subscribes to live results and cleans up page subscriptions.
localChanges.ts
Keeps the separate edit queue and projects pending changes over confirmed snapshots.

The guide is visible only to the system owner, through the same verified owner gate as the other App documents. The runtime pattern serves signed-in accounts generally; owner-only documentation does not make their caches owner-only.
