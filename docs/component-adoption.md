# Component adoption

The internal dashboard preserves the component matrix, filters, source drilldowns and freshness evidence. Its destination is `https://system.designsystem1.com/adoption` (the existing document at `https://designsystem1.com/adoption/` remains available) (it was `dash.designsystem1.com` until 20 October 2026, when that host became Design system 1's dash portal, its Feedback and Flags on 0001's System Worker). The former `/app/reports/components`, `/reports/components` and `/reports` routes redirect to the dashboard, without report data. System is linked in the owner-only documentation navigation and contains Adoption, Architecture, Examples and Constraints. The System site reuses the matrix, icon adoption and glossary directly, with its own navigation and sign-out. The retained documentation pages still render them directly in that shell. The page requires the owner session; the read-only report API revalidates that same host-only cookie (or the existing bearer token) with the authority. The separate adoption domain is removed.

The existing app sign-in supplies a Convex Auth token. Before serving the dashboard HTML, creating its browser session or reading any report data, the Worker calls `users:current` on the app's deployment and requires all three: the configured owner user ID, email `jaa90@icloud.com`, and `emailVerified: true` derived from the stored verification timestamp. Missing configuration or an unavailable identity authority fails closed. The report adds no account or sign-in provider.

Only `/app/signin` and its data-free static shell/assets are public on the dashboard host. A same-origin authenticated POST to `/api/dashboard/session` sets a host-only `__Host-` cookie with HttpOnly, Secure, SameSite=Strict and a one-hour maximum age. The cookie contains the existing session token; the Worker revalidates it with Convex on every protected HTML request. Tokens never appear in URLs. Sign-out clears the cookie and revokes the existing Convex session. The report API requires a freshly checked bearer token or the document’s host-only owner cookie; no report snapshot is bundled in the shell, assets or cookies. Protected responses are private/no-store and noindex.

## Component glossary

Component codes and individual versions appear only in Adoption, including its glossary. Official documentation headings show the component name alone, including for the signed-in owner. `shared/component-codes.json` owns both values.

Component versions start at `0.1.0` when individual tracking begins; they do not reconstruct earlier releases. They are independent of the package version. Increment the affected component's patch for a compatible fix, minor for a new compatible capability, and major for a breaking change. Keep a component's version unchanged when only another component changes.

Dash links to a searchable component glossary at `/#glossary`, with Root, Core, Unit and Page tabs taken from the canonical component directory. Search and counts apply to the selected layer. `shared/component-codes.json` owns the existing uppercase codes, with at most four characters each. Preserve assigned codes when names change; add a unique code when adding a directory entry. Codes use the DS1 monospace font. The same owner gate protects both dashboard views.

## Catalogue and layout

Column names and layer names are resolved from the shared component directory: Root, Core, Unit and Page. Every directory entry is included automatically, and unused columns are shown by default so newly added components remain visible. Root counts authored stylesheet connections to Styling, Colours and Fonts, including local CSS import dependencies; it does not count every element that inherits those foundations. Connections verify the actual stylesheet against its component manifest or Sync 1 lock and the recorded source revision. Modified or unrecorded DS1 copies need review. Unrelated local stylesheets are not inferred as DS1. Existing specialist controls keep their documented implementation names. Split compatibility uses are combined into Button and Switch into Toggle, retaining original tags and every source site in the drilldown. Chart includes its Bars, Range, Ratio and Spark elements. Spacing handle and Loading appear in this private report even though they are internal in public catalogues. Count cells use the 20px square (scaled by `--sf`) and the shared GT America compressed face.

`scripts/component-adoption.ts` reads tracked web source for the fifteen configured product and client surfaces. The studio owns names, roots, manifests, exclusions and deferrals in `0001/server/component-adoption.config.json`; the reusable scanner loads that configuration rather than maintaining a four-app list. Link remains measured but is deferred from migration recommendations. Design system 1’s own app/site are included, while its component implementation and examples are excluded. Its row is configured `"source": "direct"`: the app and site import `DS1/` at the same commit, so a DS1 site counts as DS1 when `DS1/` has no uncommitted changes, and no consumer manifest is invented for it. Only Design system 1's own checkout can be scanned this way. Several products share the studio repository, so an app is dirty only when its own folder has uncommitted changes. Native applications are outside this web-source overview. It records each checkout's revision and dirty state. Tests, generated files, vendor/shared-design internals, shared sign-in internals and development preview directories are excluded. Untracked files and native apps are outside the scan. Product components nested in a folder named `design` (such as Consistency's color library) remain included; root-level shared design snapshots and Link's `src/pages/design` demonstration routes are excluded. Tracked files need not be reachable from a running app, so this is a source inventory, not a deployment or runtime count.

A modified adapter counts as needs review even when the Lit component remains verified. Direct const document.createElement declarations joined with append/appendChild in the same scope are recognized too; a created element's literal classes count when its creation and the class write occur in the same lexical block (see Classes and attributes written in code). A native button directly composed inside a ds-button face is counted only as that shared component. Dynamic composition is not inferred. OverlayContent counts once in Dialog; its composed title, description and close control are not counted again. Composer has its own column for highlighted native writing fields. Its direct native textarea frame is not counted again. Text areas, literal checkbox/radio types and switch roles have their own columns; dynamic types remain in Input. Native choice frames directly inside ds-checkbox/ds-radio/ds-switch/ds-select are not counted again; native select controls have their own Select column. Literal color inputs and ds-color use the Color column; ds-swatch has a separate Swatch column. The native input directly inside ds-color is its frame and is not counted twice. Token and Token field count at shared adapter uses; the native input directly inside ds-token-field is its frame and is not counted twice. The field owns its composed suggestion menu, so that internal menu is not counted again. unrecognized local avatar abstractions are not inferred. Other React abstractions and dynamic names are not inferred.

### Where markup is read

Markup is read only where it is markup: `.html` and `.astro` files, JSX, Lit `html` templates, and strings written into `innerHTML`, `outerHTML`, `insertAdjacentHTML`, React's `__html` or `document.write`, plus a string that is a whole document (`<!doctype html>` or `<html>`, such as a rendered page or a server response). An ordinary string or code sample (`semantic: "<button>"`, `"<button>Get started</button>"`, `formatBlock("<p>")`) is not a site. Markup assembled before it is written is followed: a local name resolves through its lexical scope to its value and every later assignment (`=`, `+=`), a function to the strings it returns, an array to the pieces pushed onto it, and a function another file imports and writes into markup to the module that exports it. Markup written into an element created in the same block opens inside that element (and inside the shared host it is the frame of).

### Classes and attributes written in code

An element created in a lexical block, by `document.createElement`, an imported `h` or a local builder, carries what the same block writes onto it: a literal `className` (the static parts of a template or a concatenation, as in JSX), `setAttribute("class", …)` and `classList.add(…)`; a literal `title`, `data-tooltip` and a table, grid or slider role. Writes in another block or function, and dynamic values, are not inferred. A local builder is recognized by its definition, not its name: a function whose first parameter goes straight into `document.createElement`. A call with a literal tag counts like `h()`: classes come from an options object as the second argument, and from the parameter the builder writes into the element's class.

### Specimens

`data-ds-specimen` marks an element whose subtree demonstrates native HTML: in markup and JSX nothing under it counts, the element included, and a created element marked with `setAttribute("data-ds-specimen", "")` or `dataset.dsSpecimen` is not counted. Use it only for demonstrations of native elements and for hidden measuring copies, never for interface the product ships.

### Native frames of DS1 sites

A native wrapper that only frames a DS1 site counts once, as that site: an `h1`–`h6` or `p` whose only content is one `ds-text` (whitespace aside), a `ul` or `ol` whose items hold only `ds-row` (directly, or within each `li`), and elements marked `data-ds-overlay` inside a `ds-overlay` or `dialog.ds-overlay`, which DS1 draws as the dialog's header, title, description, field, footer and close. Text, an expression or another element beside the ds-text keeps the wrapper a site. In JSX, children are read directly; a list built by `.map` is not inferred. A `form` around DS1 controls stays a local Form lead: DS1 has `ds-form` for submission and validation, no DS1 sheet draws a native `form`, and the form's submit behaviour is the product's own, so calling it styles or frame would hide a real lead.

### Tooltips, disclosures, browser dialogs and tables

- **Tooltip:** a literal, non-empty `title` attribute on an element is a local site of its own, beside the element's own site. It is not counted on `abbr` (an expansion), `iframe` (an accessible name), head elements, the SVG `title` element, or React components, where `title` is a prop. `data-tooltip` is DS1's tooltip attribute: it counts as DS1 when the copied tooltip script (`0-face/tooltips.ts`, Sync 1's `root` `modules: ["tooltips"]` or a component manifest) and its imports are verified, and as needs review without one. A value set by an expression is not inferred.
- **Accordion:** a native `details` counts once as local; its `summary` is not a site.
- **Dialog:** `alert()`, `confirm()` and `prompt()`, called globally or on `window`/`globalThis`, are local sites; a function of the same name declared or imported in the file is not the browser's. DS1's promise-based `alert`, `confirm` and `prompt`, imported by name from `0-face/feedback.ts` or `0-face/feedback-overlays.ts`, count as DS1 once that copy and everything it imports match the component manifest or `sync.lock.json` and DS1 at the recorded revision (the same check as the block sheets), and as needs review otherwise.
- **Table:** a literal `role="table"` or `role="grid"` on an element that is neither a `table` nor a custom element counts as a local Table site.

### Ranges and shared parts

DS1 has no range control yet. Range inputs (`input type="range"`) and literal `role="slider"` are kept out of Input, so the Input column holds only what DS1's input can replace, and are listed in the app record's `gaps.range` with their sources. The dashboard names them under "Shared parts and known gaps".

A custom element defined in a copied shared folder (`signIn/`, `vendor/`: the shared Sign-in screen, the vendored editor) is a studio part, not product-local. It is recorded under `sharedParts` with its uses and defining file, and with the `sync.lock.json` source when the recorded hash matches the copy; without a lock, the provenance rests on the folder alone. Other unrecognized custom elements stay under `otherCustomElements`.

## Icons

Below the component matrix, the icon matrix has one row per icon and one column per app. `scripts/icon-adoption.ts` reads the same tracked files, and also the app's tracked stylesheets in its roots (a root-level `design/` or `ds1/` folder that holds none of DS1's layers is the app's own stylesheets, not a snapshot). Every site records its kind and its status, and a cell takes the status of its furthest site from DS1. The matrix filters by status and by kind; a cell's drilldown lists each site's file, line, kind, the name as written, the drawing it resolves to and its status, never source contents.

- **ds-icon:** a `ds-icon` with a literal `type` (markup, Lit, JSX, `h`/`createElement` calls, or an element named right after `document.createElement`) is a use of that name; a `type` that is an expression is a dynamic use.
- **Components:** an app's own React icon set, recognised by its shape, not its file name: a module exporting at least five components that each draw an `<svg>`, or render `ds-icon` with a literal type, directly or through a factory such as `makeIcon("X", "close")`. Imports are followed through `export *` and `export { … } from`. A component that renders a DS1 icon counts as that icon; one that draws its own SVG is local only, named after the component, and a well-known name records the DS1 icon it stands for (X → close, Trash2 → delete, Copy → duplicate, ExternalLink → up-right, ChevronDown → down). Those rows form their own group, "Local, DS1 has the icon".
- **Icon sets:** components imported from a package (Tabler, Lucide, Heroicons, React Icons, Phosphor, Radix icons) are local only, named after the set, with the same well-known names.
- **Files:** a default import of an SVG (`x-icon/*.svg` or the app's own) and an `<img src>` with a literal SVG address.
- **CSS masks:** a `mask`, `mask-image`, `-webkit-mask`, `-webkit-mask-image`, `background` or `background-image` with `url(….svg)`, in a stylesheet, a `<style>`, a style attribute, CSS in a template literal or a style object, and a custom property set to one where a mask or background reads it through `var()` (DS1's `.ds-icon` reads `--ds-icon`). `mask` and `-webkit-mask` in one rule to one file are one site. An `svg+xml` data address is a drawing of its own.
- **Icon fonts:** class lists from Phosphor (`ph ph-x`), Font Awesome (`fa-solid fa-x`), Bootstrap Icons (`bi bi-x`) and Material (the icon's name as the element's text) are local only, named after the set and the icon. The links, `@import`s and imports that load such a font are listed apart.
- **Glyphs:** a button, link, summary, control role or click target, or an element marked as an icon (hidden from assistive technology, labelled, an image role or an icon-like class), whose whole text is one symbol (× ✕ ▶ ■ ↶ ↷ ↗ ↓ ← → ★ ⋯ ▾ ▸ ◲ and similar); a glyph child of an `h`/`createElement` call; a `ds-text` whose text is one; or a glyph assigned as an element's whole `textContent`. Each maps to the DS1 icon it stands for and needs the DS1 drawing. Arrows in running text are Inter by DS1's rule and are not counted.
- **Inline SVG and script SVG:** an inline `<svg>` and a `createElementNS(…, "svg")` are drawings made in the source. When their shapes are a DS1 drawing they are named after it; otherwise they are counted apart, below the matrix, with dynamic names and icon font stylesheets.

Drawings are compared by geometry: each path is rewritten in absolute commands, horizontal and vertical lines as lines, and its numbers compared within 0.02 of a unit; paint, ids, wrappers, definitions and clips are ignored. A resolved file or pasted drawing that is DS1's is the **DS1 drawing**, even under another file name; a file named after a DS1 icon that is not its drawing **needs the DS1 drawing**; any other icon-sized drawing (at most 32 units each way, and not a logo or a code) is **local only**, named after its file. A relative address resolves from the file that names it, a root address from the nearest folder or its `public/`, or else from the one tracked SVG it ends. An address built from an expression is a dynamic use. An address that cannot be resolved to a tracked file, and a drawing named only in data, are not counted.

An app with a copied icon map beside its DS1 snapshot (`<snapshot>/2-core/generated/ds-icon-map.ts`) is compared drawing by drawing with today's DS1 map for its ds-icon and component sites. **DS1 drawing** is a match, or a use in an app without a copy. **Needs the DS1 drawing** is a copy that differs, or a DS1 name the copy lacks. **Local only** is a name DS1 does not draw. Unused copies are listed only when they differ (≠) or are local additions (+).

## Owner access and release

The app's existing owner must sign in once before access can be configured. `vp run reports:configure` checks the app's `VITE_CONVEX_URL`, reads `SIGN_IN_OWNER_EMAIL` from that deployment, requires the requested address, and resolves exactly one existing account with a matching verified user record. It makes no changes and does not print account values. Missing or ambiguous accounts stop configuration; let the owner complete sign-in rather than creating an account for them.

After hostname confirmation, follow the harness deployment policy:

1. Confirm the checkout is the intended release source and the app's backend URL matches the deployment being used.
2. Run `node scripts/configure-report-access.mjs --apply`. This writes `REPORTS_AUTH_URL` and `REPORTS_OWNER_ID` as Worker secrets. It does not modify Convex or its accounts.
3. Check the `ds-one-libraries` bucket's public access with `wrangler r2 bucket dev-url get` and `wrangler r2 bucket domain list` from `services/`. Both direct public access paths must remain disabled: only the authenticated Worker may read report data.
4. Publish the small `users:current` response addition to the app’s existing live backend (dry run before deploy); do not select the unused deployment by its production label. Bind the confirmed dashboard custom domain in `wrangler.jsonc` and test both routing and configuration.
5. Run `vp run reports:upload` to rescan and upload `reports/component-adoption.json` into that private bucket, then `vp run deploy` to publish the site and Worker. The public stylesheet routes only resolve `ds1/` keys and cannot serve `reports/` keys.
6. Verify anonymously that `/api/reports/components` returns 401, then as the owner verify the snapshot timestamp and at least one cell. Another authenticated account must get 403. Report responses use `private, no-store` and no CORS permission.

For local Worker data, run `vp run reports:scan` and `vp run reports:upload:local`. The latter targets the configured local preview bucket, without publishing anything remotely. Data is never copied into `website/public`, `website/dist`, app bundles, Pagefind, or the npm package.

## Published libraries and Markdown

`scripts/library-provenance.ts` and `scripts/markdown-sites.ts` hold these rules; the scanner calls them at a few marked points.

**Published libraries.** A library authored in the libraries app is served from `designsystem1.com/ds1/<id>/latest.css` (or an immutable `/v/<n>.css`). A product that connects one (the address appears in its tracked code or stylesheets; a brief, README or test that names it does not count) can hand native controls to it with a literal `data-library-control` attribute. Such a marked control, and each imported JSX use of a wrapper whose exported component returns exactly one marked native element, counts in that control's column (a marked link in Button, `type="checkbox"` in Checkbox, and so on) as **needs review**. Wrappers are followed through named re-exports; the wrapper's own face counts at its uses, not again. Without a connected library the marker means nothing and the elements count as before.

**A pinned library verifies.** Publishing prepares each version (`packages/css-validate/src/library.ts`): DS1's component tokens after the library's `--one-*` tokens, the button-link faces, and a first line naming the DS1 library revision (`DS1/1-root/library-tokens.ts`). Sync 1's `library` export copies one version, `ds1-library/<id>/v/<n>.css`, unchanged, with `ds1-library/library-manifest.json`; `sync.lock.json` hashes both at a DS1 commit. The library's sites count as **DS1 styles** when the app's tracked code or stylesheets load that copy and no library address, and the copy verifies: the lock records a DS1 commit and both files, neither was changed, the manifest names the same library, version and hash, and the stylesheet's stamp names the manifest's revision.

Everything else stays **needs review**: a library loaded from its address (`latest.css` changes with every publish; a remote `v/<n>.css` has no lock), a copy edited or rewritten after the sync, a copy without the stamp, or a lock taken from uncommitted DS1 source. Verification establishes which published version, prepared by which DS1 rules, draws the site; its colours and corners are still its owner's. Native text that a page-wide library sheet may also draw is not inferred: which components render on which pages is composition, as with prose.

**Markdown and MDX.** `.mdx` files, and `.md` files in an Astro project's `src/pages` or `src/content`, are read under the configured roots. Other Markdown is not: READMEs and licences, and text an app imports as data for its own renderer, whose templates already count once, like a loop. Each paragraph and heading counts in Text, each list once in List and each table once in Table, at the line its block starts. They are DS1 styles through a verified `prose.css` only where DS1's prose sheet draws them: in a Starlight site whose `MarkdownContent` component wraps its slot in an element marked `data-ds-prose`, the documents in `src/content/docs`. The nearest `data-ds-prose` or `data-ds-not-prose` element written in the document still decides. Any other renderer, including a site's own `.prose` class, leaves them local text. HTML in Markdown and markup and component uses in MDX are read like markup, and MDX imports resolve shared adapters; code blocks, inline code, frontmatter and MDX imports and exports are not sites.

Design system 1's own docs content is in its row: the site is a documentation site, its writing is its page content, and marketing pages elsewhere count their text the same way whether it is written in HTML or Markdown. It adds several hundred DS1-styled prose sites, drawn by DS1's own prose sheet; that is correct, and it leaves the row's local count unchanged. The specimens inside the docs are example components the scanner does not recognize, so they are not counted.
